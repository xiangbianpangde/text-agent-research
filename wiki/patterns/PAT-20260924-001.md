## 症状 / 场景

判据确实被写下来（测试/负例/文档 §），也『已实测对当前代码失败』，但调用它需要**手工编辑源码**（删掉 skip、改掉守卫、注释掉断言）。于是：①修复者读代码认为已修复后，没有任何东西会告诉他不是——判据在那里却无法被不编辑源码的人执行；②复核者只能引用『已实测失败』这一**过去时**记录，无法在自己手上复跑，把结论从可复验降级为可引用；③撰写者本人也容易把「判据存在」当成「判据生效」。0289 一例的原始写法是「置于 skip，修复落地后取消 skip 即成门禁」——『取消 skip』是动作，不是入口。

## 根因

把判据的**文本**与判据的**入口**当成一回事。写出可运行文件只完成一半；若唯一的调用方式是编辑该文件，则判据的启用本身变成一次未记录的手工操作，且这次操作没有 owner、没有时机、没人会被提醒漏做。越是关键（安全边界）的判据越容易这样：因为『先 skip 保套件绿』在当时是正确决定，而它把入口留给了未来某次人工编辑。

## 可执行对策（workaround）

给判据一个**不改源码即可调用**的开关：环境变量门禁（如 M3_REQUIRE_0189_FIX=1 npm run test:catalog）比『取消 skip』好，因为：①修复者可自行复跑，不必编辑被测仓库；②复核者可独立复现同一命令；③默认路径逐字不变（保持套件绿），但启用时必然失败且明确报出复现消息；④把『已修复』变成一个可执行断言而非宣言。配套三条纪律： (a) 门禁默认关闭——长期带红的套件会被学会忽略，那时失败不再传递信息； (b) 双向实测（开门禁必须失败且给出复现消息；默认必须逐字不变），不得只测一侧； (c) 在文档与 README 里写出该命令，因为修复者不会先读测试源码。

## 证据

ISSUE-0189（M3 credential proxy 无 nonce 校验）：判据 catalog/test/recovery.test.ts 已落地并『实测对当前代码失败』（commit b65aa33），但入口只有『取消 skip』。改为条件式 skip 后（commit 03566be），M3_REQUIRE_0189_FIX=1 → error 'no credential header: must be refused with a definite 4xx, got 200'，# pass 231 # fail 1 # skipped 0，exit 1；默认 → # pass 231 # fail 0 # skipped 1，exit 0。同源现象另见：ISSUE-0180/0182（--run 可绕过必须先通过的 preflight；测试自身能写付费观测归档）——三者共同点是『约束存在但无可执行入口』。开门禁输出的 not ok 52 为外层 suite 节点转述子失败（subtestsFailed），非第二处缺陷；按 not ok 计数会多算。
