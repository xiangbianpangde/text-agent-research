## 症状 / 场景

一个门禁（preflight / 断言 / 校验器）报告通过，而它要防的那件事正在发生。典型形态：门禁的判据是「实际值 == 期望值」，而期望值由被检查代码的同一条表达式算出；一旦某个输入让该表达式溢出、饱和或被截断（如 1e308 × 100 → Infinity），两侧同时变成同一个不可用值，等式退化为 x == x，恒真。所有「存在性 + 正负」检查（typeof、> 0、!= null）对 Infinity/NaN 也各有漏洞，故它们无法兜住。

## 根因

期望值与实际值同源，门禁缺少独立参考。检查的是「输入合法」而不是「被使用的派生量合法」——两者之间隔着一次算术。更深一层：门禁作者把「值来自我自己的推导」当成可信来源，而推导本身正是要验证的环节。

## 可执行对策（workaround）

① 门禁必须持有一个不来自被检查代码的参考（独立推导的上界、契约常量、具体字面值），或至少对被检查的检验量做独立域校验：Number.isSafeInteger 而非 isFinite，并明确安全边界。② 校验点在「使用处」而非「解析处」：每个消费该数值的 API 都自己拒一次，不只解析器拒。③ 反向验证时不能只问「测试会不会红」，要问「什么输入能让这道门禁恒真」——形态上就是找让两侧一起变坏的输入。④ 对任何派生的数值上限，先算一遍 Number.isSafeInteger(派生值)，再谈它等于不等于期望。(5) 抽成纯函数以便能直接变异——内联在 preflight 里的判据，单测套件永远跑不到。
